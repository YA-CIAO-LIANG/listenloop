# AI 模擬使用者測試報告

> **這不是真人測試。** Claude 依 `docs/personas.md` 的角色「出聲思考」，用 Playwright 實際操作 E2E 版網站（2026-11-09：7 個角色、手機 375 px 與筆電；2026-11-13 起：10 個角色、四種身分的完整流程，iPhone 15、Pixel 7 與筆電，D170）。網站使用假的 Supabase、假的 AI 和付款供應者，沒有呼叫 Azure。
>
> 這種測試適合抓明顯的問題，例如版面、按鈕大小、文字、流程斷點。但它猜不到真實使用者的動機與誤解，上線前仍建議找 3～5 位真人照同樣的任務做一次。

## 怎麼跑

```bash
npm run build:e2e
USABILITY_ROUND=1 npm run usability   # 截圖與量測寫到 usability-results/round-1/（不進 git）
# 和其他工作目錄同時跑時，build:e2e 與 usability 都加上 MOCK_SUPABASE_PORT=… E2E_PORT=…
```

- 任務定義在 `usability/tasks.spec.ts`，每一步都會截圖並量測：
  - 是否超出螢幕寬度，以及造成的元素；
  - 手機上小於 44 px、筆電上小於 24 px 的點擊目標（段落裡的文字連結不算，依 WCAG 2.5.8）；
  - 第一屏的字數、最長段落、平均句長；
  - axe（WCAG 2.1 AA）違規。
- Claude 再看截圖，依角色判斷問題並評嚴重度。
- 下一次要再跑，用 skill `ai-usability-test`。

## 嚴重度（Nielsen 0～4）

| 分數 | 意思                       | 處理                       |
| ---- | -------------------------- | -------------------------- |
| 4    | 災難：無法完成任務         | 一定要修                   |
| 3    | 嚴重：很多人會卡住或犯錯   | 這一輪就修                 |
| 2    | 次要：會造成困擾或拖慢速度 | 小的這一輪修，大的列入待辦 |
| 1    | 外觀：有空再修             | 只列出來                   |
| 0    | 不算問題                   | —                          |

### 需要 Joe 決定的事（護欄擋下的修改、角色之間的衝突）

1. **班級方案的老師分鐘數**（P10）：45／70／105 分鐘是照「成本 ≤ 月費 25%」算的（D173）。老師覺得備課不夠；要提高，就要提高月費、放寬 25% 的規則，或另外賣加購分鐘數。
2. **F16 額度依當地時區重設**（P9）：目前一律是台灣午夜。
   - **2026-11-14 Joe 決定（D180）**：維持台灣午夜；「我的額度」的說明改寫清楚，寫明是台灣時間的午夜重設、換算成你的時區顯示。
3. **F10 播放速度提示的頻率**（免費帳號每個練習頁都顯示）。
4. **F15 第 7 天結果頁的主要按鈕**：要不要只留「選下一份教材」。
5. **F11 每頁上方的同意提示**（P5）：長輩希望少一點干擾，但這是法律告知，改法要 Joe 決定（例如只在第一次與條款更新時顯示）。
   - **2026-11-14 Joe 決定（D180）**：按過一次就不再顯示；登入者存在帳號，換裝置也記得；帳號頁和頁尾可以重看。
6. **付款的人不是使用者**（P1、P2）：要不要做「家長付款連結」或禮物卡？這是新功能。
7. **字放大 200% 的首頁**（P5）：需要在真機上確認。
8. **ZAP 掃描提示**（擋住 PR #235 價格實驗）：見報告。

- 角色之間的取捨（記在 D179）：長輩要更大的字和更少提示、上班族要精簡；這次的修改都是加清楚的下一步或拿掉重複的文字，對兩邊都有利，沒有為單一角色放大版面。
