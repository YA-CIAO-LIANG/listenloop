**觀察**：

- **一次就過的 PR 越來越多**：M0～M2 平均每個 PR 要改 3～7 次，之後穩定在 1.0～1.5 次。原因是本機先跑完五項檢查加 E2E 才推送（CLAUDE.md 工作規則），CI 很少失敗。
- **最近一批 6 個錯誤修正的 PR 平均改了 3.2 次**，是 M2 之後最高的。原因：
  - 同時跑兩輪 QA，造成假的發現；
  - E2E 偶發失敗，追查後發現是真的同步錯誤（D149）；
  - 拖曳測試重寫了幾次。
- **修正 eval 這批每項約 1 小時**，比平常久：提示詞要用真實 API 錄製與評分，講解的修正試了 4 次才同時做到「長句變短」與「一般句子不退步」（D153）。
- **危機預防與資安這批 8 個 PR 平均 1.1 次就過**：每個 PR 都先跑完本機五項檢查和完整 E2E。唯二的重推，一次是新元件沒有加進翻譯檔使用清單（只看 git 追蹤檔的測試，本機沒抓到），一次是 gitleaks 在 CI 擋下文件裡引用的誤報原文；兩者都證明 CI 的檢查有在運作。
- **CI 加合併的中位數約 4 分鐘**，等待時間不是瓶頸；真正花時間的是本機的完整 E2E 和 QA 掃描。

**下次怎麼更有效率**：

1. **一次只跑一輪 QA 或一組 E2E**，因為它們共用 port 3200。同時跑會造成假的發現，這次多花一輪約 10 分鐘。
2. **偶發失敗先當成真的錯誤追查**：這次的不穩定 E2E 最後證實是同步的競爭條件。先追查比重跑省時間。
3. **Joe 回報的錯誤先重現再修**：先寫一個在舊程式會失敗的測試。沒辦法重現的（例如 D140）要明確說明，並列出請 Joe 重新測試的步驟。
4. **大功能先做假門或原型**：魚缸（M2.5）做了 6 個 PR（整批約 23 小時），之後關閉；學生方案（D144）改用假門先驗證需求，是比較好的做法。
5. **AI 相關的改動先跑 eval**：以前提示詞改了只能抽看一兩個例子，D117 和 D123 都是上線後才發現。現在 eval 只要 US$0.04，就能一次看 54 種情況。
6. **提示詞的修改只影響需要改的請求**：這次讓一般句子的講解提示詞維持不變，11 筆講解沿用舊錄音，只重錄 1 筆，省下約 US$0.015。
7. **進度報告和文件集中在最後一個 PR**：文件 PR 在 CI 只跑格式檢查（D134），不佔 E2E 時間。
8. **會改變全站狀態的 E2E 獨立成最後才跑的專案**（D155 的 `ops`）：緊急開關會影響同時進行的其他測試，放在一起跑會產生假的失敗。
9. **新的自動檢查先在本機對整個歷史跑一次**：gitleaks 先掃完 418 個 commit、把誤報寫進允許清單，CI 上線後才不會一開始就擋住所有 PR。
10. **平行開發先把共用資源參數化**：E2E 的埠號改成環境變數（#214）之後，4 個代理才能同時跑完整 E2E 而不互相關掉伺服器。
11. **大家都會改的檔案用「新增在結尾」的格式，並準備自動合併的腳本**：`docs/decisions.md` 每個 PR 都加在結尾，衝突時兩邊都保留即可，可以用一個小腳本自動處理（rebase、兩邊都保留、重新推送）。
12. **衝刺月份一開始就看 Actions 分鐘數**：這次到中途才發現用了 1,720／2,000 分鐘。月初衝刺前先跑 `npm run actions:usage`，預估會超過就先開 `CI_LITE`，E2E 改在本機跑。
13. **平行的 PR 依 migration 日期與依賴順序合併**：先合併 migration 日期較早、被依賴的 PR，再 rebase 下一個；用 `git rebase --onto` 跳過已經 squash 合併的 commit，避免重播舊的 commit 產生衝突。
14. **假 Supabase 缺的功能先補上，再測流程**：班級流程原本完全不能在 E2E 跑，補上之後 AI 虛擬使用者測試才找到「截止日預設當天」與「學生沒有下一步」兩個問題。
